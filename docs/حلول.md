# توثيق الحلول

## المشكلة 1: روابط فيديو يوتيوب "مسمومة" عبر النفق (403 / ERR_FAILED)

**الظاهرة**: طلبات `googlevideo.com` الناتجة من صفحة يوتيوب عبر الوكيل تفشل — أحياناً 403، وأحياناً
روابط صالحة الشكل تُرجع خطأ في المتصفح (`ERR_FAILED`) رغم نجاحها عبر `curl`.

**السبب الجذري**: عند تمرير صفحة يوتيوب عبر النفق، يصدر المتصفح طلبات `player API` من نطاق النفق.
يوتيوب يربط تلك الطلبات بسياق البصمة (PoToken/nsig + Origin) ويصدر روابط تدفق **مسمومة عمداً**:
قيمة `expire` المستقبلية البعيدة (مثل `8659028621` = سنة 2244) تشير إلى أن الرابط لن يُقبل فعلياً —
إجراء مضاد لوسائل التجاوز. لا يُصلح ذلك بتزييف `Origin`/`Referer`/الكوكيز على مستوى المتصفح،
لأن الرابط مسموم من داخل الرد (server-side).

**الحل**: لا تُمرر صفحة يوتيوب عبر الوكيل للفيديو أصلاً. بدلاً من ذلك، يُولد الرابط **على الخادم**
عبر `yt-dlp` (sidecar) الذي يفك تشفير `nsig` بنفسه، ويبثه الخادم للعميل. المتصفح لا يلمس
`googlevideo` إطلاقاً — لا PoToken ولا CORS، وIP الخروج ثابت دائماً.

## المشكلة 2: أسماء تنسيقات HLS غير متاحة في `web_safari`

**الظاهرة**: `yt-dlp -f hls-720` يفشل بـ "Requested format is not available" رغم أن `hls/best` يعمل.

**السبب**: في `player_client=web_safari` أسماء التنسيقات هي أرقام itag (91=144p، 92=240p،
93=360p، 94=480p، 95=720p، 96=1080p) وليست أسماء `hls-*`.

**الحل**: خريطة جودة مغلقة (server-side) تربط الاسم المطلوب بسلسلة fallback
(مثل `hls-720` → `95/94/93/92/91/hls/best`) — يختار yt-dlp أول متاح، وأي اسم غير معروف
يُسقط افتراضياً (لا يُمرر إلى yt-dlp إطلاقاً).

## المشكلة 3: 403 عند جلب مقاطع HLS عبر الخادم بينما curl ينجح

**الظاهرة**: جلب المقطع عبر مسار الوكيل يعيد 403 من googlevideo، بينما نفس الرابط من نفس
الجهاز عبر `curl` يعيد 200.

**السبب**: `reqwest` يطبّع الـ URL تلقائياً — يفك `%3D` إلى `=` و`%3B` إلى `;` في المسار،
فيصل googlevideo sparams مفسودة فيرفض (403). المشكلة لا تظهر مع curl/Node لأنهم لا يطبّعون
بنفس الطريقة.

**الحل**: لا تفك ترميز القيمة في الـ handler إطلاقاً — مرّر `u` المشفّر كما هو إلى `reqwest`
(الطباعة الذاتية تفك طبقة واحدة فقط وتعيد الشكل الصحيح). الترميز في القائمة يجب أن يرمّز
`%` و `&` و `=` و `?` و `#` ويُبقي `/` و `:` خام (ضغط الروابط تحت حد Cloudflare 8KB).

## المشكلة 4: عملية الخادم تموت عند انتهاء أمر الغلاف

**الظاهرة**: `nohup ... &` يعمل أثناء الجلسة ثم يموت عند انتهاء الأمر حتى مع `disown`.

**الحل**: الجلسة نفسها تُقتل (بيئة sandbox)؛ إعادة التشغيل عبر أمر منفصل فوري:

```bash
nohup env PROXY_PASSWORD="$(cat ~/ytproxy-secrets/.env.password)" RUST_LOG=info PORT=8081 \
  /home/youssef-ayad/ytproxy/target/release/ytproxy > /tmp/opencode/ytproxy17.log 2>&1 < /dev/null &
```

ملاحظة: تجنّب `pkill -f "target/release/ytproxy"` داخل نفس الأمر — النمط يطابق سطر أوامر
الغلاف نفسه ويقتله.

## خارطة الحل

المتصفح ──> /ytstream-hls?video=<id>&quality=hls-1080 ──> الخادم

المتصفح ──> /ytstream-hls?u=<googlevideo-enc> ──> الخادم ──> googlevideo (200/206)

## المشكلة 5: HTTP 400 من www.facebook.com عبر الوكيل (بينما curl المباشر و static.facebook.com يعملان)

**الظاهرة**: المتصفح عبر النفق يحصل على 400 "Sorry, something went wrong." من www.facebook.com، بينما:
- curl المباشر من نفس الجهاز يعمل (200)، و
- static.xx.fbcdn.net عبر الوكيل نفسه يعمل (200).

**السبب الجذري — مثبت تجريبياً من نفس الجهاز ونفس الـ IP (102.132.103.35)**:
فيسبوك يطبّق **قاعدة فورية على مستوى موازن التحميل (SLB)**، لا قائمة حظر IP:
- جواب الـ 400 يحمل `proxy-status: http_request_error` و `server-timing: slb_rule_lat;dur=0` — القرار لحظي من قواعد البصمة/الترويسات.
- القاعدة: **"UA يدّعي متصفحاً (Chrome/Firefox) + اتصال لا يشبه متصفحاً = 400"**. أما UA صادق (curl) فنفس الاتصال يُخدم 200.
- الوكيل يمرّر UA المتصفح الوارد كما هو (`FORWARD_HEADERS` يشمل `user-agent`، proxy.rs:92-104) لكن خروجه غير متصفح إطلاقاً: TLS OpenSSL عبر native-tls، HTTP/1.1 فقط (`http1_only`)، لا ترويسات Sec-Fetch، ولا ضغط — فيكتمل شرط القاعدة → 400.
- هذا يفسر كل الملاحظات: curl المباشر ينجح (UA صادق)، static يعمل عبر الوكيل (CDN ثابت بلا قاعدة SLB)، والمتصفح عبر النفق يفشل (UA متصفح عبر بصمة غير متصفحة).

**جدول الأدلة التجريبية** (من نفس الجهاز، نفس الـ IP):

| العميل الخارجي | UA الخارجي | النتيجة |
|---|---|---|
| curl (h1 / h2 / no-alpn / أي ترتيب ciphers) | Chrome 126 | **400 دائماً** |
| curl | curl/8.5.0 | 200 |
| curl | Firefox 128 | **400** |
| curl_cffi impersonate=chrome124 (بصمة Chrome كاملة) | Chrome 124 | **200** |
| ytproxy (native-tls + http1_only + accept-language) | curl/8.5.0 (ممرَّر من العميل) | 200 |
| ytproxy | Chrome 126 (ممرَّر من العميل) | **400** ← إعادة إنتاج الظاهرة بالضبط |
| ytproxy → static.xx.fbcdn.net | أي | 200 |

### (أ) ماذا يفعل فيسبوك تقنياً

فحص **تناسق الهوية** (UA ↔ بصمة TLS/HTTP) على حافة SLB: إذا ادّعى العميل متصفحاً ولم تطابق البصمة (مثل بصمة curl/OpenSSL الشهيرة، غياب HTTP/2 وترتيب ترويسات المتصفح و Sec-Fetch) → صفحة خطأ عامة 400 فوراً. الـ IP نفسه ليس محظوراً — الشرط مقرون بالـ UA (إثباتنا: 200/400 من نفس الـ IP يتغيران مع الـ UA فقط، بنفس بصمة TLS تماماً).

مصادر داعمة:
- https://medium.com/@cyberyozh/digital-proxy-footprints-how-do-facebook-google-actually-determine-that-you-are-using-a-proxy-ef3d4e84ca86 — "Digital proxy footprints": JA3 يكشف "المتصفح الخاطئ" (بوت/أتمتة) وليس الوكيل نفسه عند الوكلاء الشفافة، وأنظمة ميتا تحلل **الاتساق** بين UA وطبقات الاتصال.
- https://github.com/seanmonstar/reqwest/issues/2202 — مواقع (مثل api.figma.com) تعيد 400 بجسم HTML عند تغيّر طبقة TLS/HTTP الخاصة بالعميل — نفس نمط الظاهرة.
- https://github.com/facebook/facebook-python-business-sdk/issues/368 و https://stackoverflow.com/questions/33822789/facebook-oauth2-sorry-something-went-wrong — نمط فيسبوك المعروف: 400 + HTML "Sorry, something went wrong" للعملاء العامين/غير المتصفحين.

### (ب) حلول المجتمع

- **curl-impersonate** (https://github.com/lwthiker/curl-impersonate) — بنية curl تحاكي بصمة Chrome/Firefox كاملة (ترتيب TLS + HTTP/2 + ترويسات) — الحل القياسي لعملاء "يدّعون متصفحاً".
- **curl_cffi** (https://github.com/lexiforest/curl_cffi) — نفس الفكرة بواجهة Python؛ **اختبرناه هنا: chrome124 → 200 من نفس الـ IP**.
- **veil** (https://github.com/adtyapnda/veil) — متسلق متدرج http_basic → tls_impersonate → browser؛ يجسّد التسلسل الصحيح للتصعيد، مع اعترافه بأن الحظر القائم على السمعة (reputation hard-block) لا يُجتاز بانتحال TLS وحده.
- تحذير مقال Medium: الانتحال الجزئي لا يكفي — يجب تطابق كل الطبقات (UA + TLS + TCP + سلوك)؛ حالتنا تحديداً تتطلب UA↔TLS فقط.
- (حلول حظر الـ IP مثل zapret/الوكلاء السكنية تعالج مشكلة مختلفة — DPI/سمعة الـ IP — ولا تنطبق هنا لأن الـ IP غير محظور أصلاً.)

### (ج) الرأي الموثق: الحل موجود برمجياً

**ليست سياسة حظر IP غير قابلة للاجتياز** — الدليل الحاسم: نفس الـ IP يعطي 400 أو 200 حسب اتساق الهوية فقط، و curl_cffi(chrome124) نجح من نفس الـ IP فوراً. أمامنا حلان:

1. **فوري (سطران في ytproxy)**: لا تمرر UA المتصفح نحو فيسبوك — أرسل UA صادقاً (`curl/8.5.0` أو `ytproxy/1.1`) بدلاً من الممرَّر → 200 (مثبت عبر الوكيل نفسه أعلاه). مناسب لعرض الصفحات العامة/واجهة الدخول.
2. **أمثل للجلسات**: بصمة Chrome كاملة عبر curl-impersonate كـ sidecar (نفس نمط yt-dlp الموجود في المشروع) → 200 مع بقاء UA المتصفح.
3. **حد الاجتياز**: بعد تسجيل الدخول بحساب، تُطبَّق أنظمة سمعة وسلوك أدق (التصفح العادي في حدودها؛ الإدارة الجماعية للحسابات خارج نطاق وكيل HTML وتحتاج IP سكني/موبايل — المصدر: مقال Medium أعلاه).

### الإصلاح المطبّق في v1.1.1 (مثبت في المتصفح عبر النفق)

في `proxy_request` (proxy.rs):
1. `is_fb`: صحيح لأي `*.facebook.com` أو `*.fbcdn.net`.
2. في حلقة `FORWARD_HEADERS`: أُسقط `user-agent` الوارد من المتصفح عندما `is_fb`.
3. كتلة الـ UA: للفيسبوك نرسل `curl/8.5.0` صادقاً دائماً (200 مثبت) — باقي المواقع لا تتغير
   (المتصفح بلا UA → `DEFAULT_UA`).

النتيجة في المتصفح عبر النفق: صفحة الدخول كاملة (Log in to Facebook) بدل "Sorry, something went wrong".
قوقل ويوتيوب والشعارات لم تتأثر. حد الاجتياز: بعد الدخول بحساب، أنظمة السمعة/السلوك أدق —
التصفح العام يعمل؛ الإدارة الجماعية تحتاج IP سكني (مصدر: مقال Medium أعلاه).
